Quickstart and SDK usage.

Quickstart

1. Start it

ActaSeal runs in your own infrastructure under Docker Compose:

docker compose up --build

A demonstration set-up starts with sample users and nothing to configure. A production deployment uses your own database, signing key and administrator account. The deployment guide supplied with the software gives the exact settings for each.

2. First-run setup

Sign in with the administrator account you set at start-up, or through your identity provider. A fresh production deployment has no policy loaded: it is healthy, and it refuses every decision with a named reason until you load one.

3. First receipt

With a policy loaded, every decision the gateway makes produces a signed receipt. A runnable end-to-end example, including a real signed receipt with a bound terms_hash, is included with every deployment.

4. Verify offline

actaseal verify-receipt --receipt receipt.json --ledger ledger.json --keys keys.json

Or, with no ActaSeal installation at all -- only the public key and the standalone verifier -- use verify.actaseal.com.

API reference

Every deployment serves the reference for its own API, so what you read always matches the version you are running. Most integrations do not need it: the SDKs below make the calls.

SDKs

Python

from actaseal.sdk.thin_client import ActaSeal

guard = ActaSeal(
    "https://gateway.example.com", api_key="...",
    policy_id="refunds_policy", policy_version="refunds_policy.v1",
)
decision = guard.guard({"action_type": "refund_request", "money": {"amount": "50.00", "currency": "USD"}})

TypeScript

The TypeScript SDK is not published to npm. It is supplied as a package file on request, and installed from that file rather than by name. The snippet below shows its API; it runs after that package is installed.

import { ActaSeal, ActaSealBlocked, ActaSealApprovalRequired } from "@actaseal/sdk";

const guard = new ActaSeal("https://gateway.example.com", { apiKey: process.env.ACTASEAL_API_KEY! });
const sendRefund = guard.wrap(
  (amount) => fetch("/internal/refund", { method: "POST", body: amount }),
  (amount) => ({ action_type: "refund_request", money: { amount, currency: "USD" } }),
);

LangChain / LangGraph

from actaseal.sdk.integrations.langchain_tools import guard_langchain_tool

guarded_tool = guard_langchain_tool(guard, my_refund_tool, action_type="refund_request")
# BLOCK -> langchain_core.tools.ToolException (surfaced to the model as a tool error)
# APPROVAL_REQUIRED -> ActaSealApprovalRequired re-raised for your own retry/escalation logic

OpenAI Agents SDK

Wrap the plain function first, then hand the wrapped function to the SDK to make the tool.

from agents import function_tool
from actaseal.sdk.integrations.openai_agents_tools import guard_openai_agents_tool

guarded_send_refund = guard_openai_agents_tool(guard, send_refund, action_type="refund_request")
refund_tool = function_tool(guarded_send_refund)
# A blocked or approval-held call does not run send_refund; the model sees a tool error.

Both adapters are optional imports -- actaseal imports cleanly with neither framework installed.

MCP

To put ActaSeal in front of an MCP tool server, run the proxy as its own process and point your agent's MCP server setting at it instead of at the tool server:

python -m actaseal.mcp --config proxy.json

Every tools/call is decided first. Only an allowed call is forwarded to the tool server; a blocked or held call is answered by the proxy and never reaches it.

Two limits of the proxy, stated rather than left to be found:

  • Every mapped tool call must carry an amount and currency. The proxy is built for tools that move money or commit to a customer.
  • The proxy cannot attach evidence to a call. A tool whose policy requires evidence is held, not allowed and not sent for approval. For those tools use one of the SDK adapters above, which pass evidence with each call.
